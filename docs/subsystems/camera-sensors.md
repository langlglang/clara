# Camera and sensor handoff

**Orientation update (implemented in code; physical result unverified):** the installed camera is mounted upside down. The Pi rotates each captured JPEG’s pixels 180 degrees in memory before either local preview or cloud inspection. A decode failure or oversized rotated frame fails capture; no raw frame is uploaded as a fallback. A small image test verifies the corner mapping. The owner verified that camera inspection worked before this orientation change; the rotated view still needs a live check.

Clara uses fictional scenarios and consenting volunteers; it will never be used on a patient. The user aims the movable camera and explicitly captures one frame for a demo question. The frame returns an observation with time and uncertainty. A failed or blurry frame produces “cannot tell,” not a guessed finding.

The selected [InnoMaker USB camera](https://www.amazon.com/dp/B0H26BG9RP) is detected by the Pi as a V4L2 MJPEG camera. The movable mount and close-up focus still need a physical check. **Demo implemented in code:** `box/src/camera/capture.ts` captures one 640×480 JPEG into memory through the camera's stable `/dev/v4l/by-id` path when available. It enforces a 4 s deadline, 1.5 MB cap, JPEG markers, session match and one-time consent. Local-preview permission stays separate from cloud use. For the current cloud path, the bystander explicitly asks Clara to take a photo or use the camera; that same spoken request grants one cloud-bound frame, with no second confirmation turn. Clara says it will send the frame to its cloud. An unrelated mention of the camera grants nothing. Each capture consumes its grant, including failed captures. The Pi caller must clear the JPEG buffer after its one use and never put it in ordinary logs. **Hardware smoke verified:** the Pi captured one valid JPEG from the stable InnoMaker device path, without saving or uploading the image, then cleared the buffer. A later live attempt exposed a Node subprocess failure to open `/dev/stdout`; `v4l2-ctl --stream-to=-` produced a valid JPEG in the same Node context and is now used by the capture adapter. Close-up quality, consent dialogue, and cloud interpretation are not yet end-to-end verified. The cloud classifier now uses constrained JSON output and includes neutral body-part and color categories; a camera result still needs the user to confirm what the image may show. Privacy-safe diagnostics distinguish a failed local capture, a failed cloud request, and an unavailable model observation without logging the frame. The screen gives separate capture and analysis failure messages rather than describing either as a blurry photo.

**Camera analysis follow-up, 2026-11-14:** A live attempt reached the cloud but its model description failed the local bounds. The parser now accepts longer bounded descriptions, drops unsafe individual fields, and rejects truncated output. A rejection log contains only stop reason and character count, never the frame or description. This fix is implemented in code; another physical photo test is still needed.

The `sensor.read` tool **must read real connected hardware**. The team selected an [Amazon MAX30102 breakout pack](https://www.amazon.com/dp/B07ZQNC8XP), wired by 3.3 V I²C to the ESP32; the ESP32 sends new samples to the Pi over their existing USB cable. Direct Pi I²C is an alternative. This breakout outputs optical samples, not a ready-made pulse number. **Demo implemented in code:** `box/src/sensors/pulse-reader.ts` starts a bounded ESP32 pulse window only after a request, listens to new pulse events, returns a BPM only when the firmware reports `quality:valid`, and stops the stream on result, timeout, cancellation or disconnect. Early unavailable reports no longer end the window before enough beats can arrive. A null or suspect result has no numeric BPM. The window can take up to 20 s because the firmware needs several consistent beat intervals. It never uses the simulator as a hardware reading. **Hardware verified on 2026-11-14:** after flashing `clara-0.2.1`, a 20-second finger-on capture returned 16 valid reports at 83–94 BPM (median 88), while a six-second no-finger capture returned only unavailable reports and no number. The spoken Clara request and accuracy against an independent reference remain unverified. See [sensor selection](../sensor-selection.md).

The camera listing includes a microphone. Explicitly select the separate MillSO mic for voice input so the audio route does not change when the camera is attached. **Demo implemented:** a USB u-blox 7 GNSS receiver is attached to the Pi, with a local 9600-baud adapter that parses checksummed RMC and rejects invalid or stale fixes (15 s since receipt, 30 s since fix time). Mock SOS coaching may show fresh coordinates with UTC fix time; otherwise it shows `Configured box address: 1455 California Ave`. The fallback is not a measured fix. A live outdoor fix on the installed receiver is **unverified**. This path does not send location to cloud or volunteers. The parser follows the [u-blox 7 receiver protocol specification](https://content.u-blox.com/sites/default/files/products/documents/u-blox7-V14_ReceiverDescriptionProtocolSpec_%28GPS.G7-SW-12001%29_Public.pdf).

Any displayed sample or derived pulse value shows value, unit, device and time without an extra experimental badge. Only show BPM from a fresh `quality:valid` event; do not call a computed value a direct chip reading. The agent can describe the result but does not use it to diagnose or choose the fictional scenario's steps. A consenting volunteer starts each reading; measurements are not stored by default.

Use [sensor contracts](../contracts.md) and [hardware notes](../hardware-power.md). Acceptance: real fresh reading, reconnect, no reading, wrong device, and volunteer change are tested on the selected hardware.
