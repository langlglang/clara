# Camera and sensor handoff

Clara uses fictional scenarios and consenting volunteers; it will never be used on a patient. The user aims the movable camera and explicitly captures one frame for a demo question. The frame returns an observation with time and uncertainty. A failed or blurry frame produces “cannot tell,” not a guessed finding.

The selected [InnoMaker USB camera](https://www.amazon.com/dp/B0H26BG9RP) is detected by the Pi as a V4L2 MJPEG camera. The movable mount and close-up focus still need a physical check. **Demo implemented in code:** `box/src/camera/capture.ts` captures one 640×480 JPEG into memory through the camera's stable `/dev/v4l/by-id` path when available. It enforces a 4 s deadline, 1.5 MB cap, JPEG markers, session match and one-time consent. The local-preview prompt explicitly keeps the photo on the box. A separate cloud-interpretation prompt explicitly asks permission to send one photo to Clara's cloud; a local-preview grant cannot authorize that upload. The reply must be the clear spoken phrase requested by the prompt, within 60 s. Each capture consumes its grant, including failed captures. The Pi caller must clear the JPEG buffer after its one use and never put it in ordinary logs. **Hardware smoke verified:** the Pi captured one valid JPEG from the stable InnoMaker device path, without saving or uploading the image, then cleared the buffer. Close-up quality, consent dialogue, and cloud interpretation are not yet end-to-end verified. The cloud classifier now uses constrained JSON output and includes neutral body-part and color categories; a camera result still needs the user to confirm what the image may show. Privacy-safe capture and cloud-status diagnostics distinguish an unavailable local frame from an unavailable cloud observation on the next authorized attempt.

The `sensor.read` tool **must read real connected hardware**. The team selected an [Amazon MAX30102 breakout pack](https://www.amazon.com/dp/B07ZQNC8XP), wired by 3.3 V I²C to the ESP32; the ESP32 sends new samples to the Pi over their existing USB cable. Direct Pi I²C is an alternative. This breakout outputs optical samples, not a ready-made pulse number. **Demo implemented in code:** `box/src/sensors/pulse-reader.ts` starts a bounded ESP32 pulse window only after a request, listens to new pulse events, returns a BPM only when the firmware reports `quality:valid`, and stops the stream on result, timeout, cancellation or disconnect. Early unavailable reports no longer end the window before enough beats can arrive. A null or suspect result has no numeric BPM. The window can take up to 20 s because the firmware needs several consistent beat intervals. It never uses the simulator as a hardware reading. **Hardware check on 2026-11-14:** a direct 12-second Pi→ESP32 run received 11 on-finger `suspect` results, and separate raw reads advanced with optical samples; the sensor and USB link work, but no stable BPM has been verified. See [sensor selection](../sensor-selection.md).

The camera listing includes a microphone. Explicitly select the separate MillSO mic for voice input so the audio route does not change when the camera is attached. **Demo implemented:** a USB u-blox 7 GNSS receiver is attached to the Pi, with a local 9600-baud adapter that parses checksummed RMC and rejects invalid or stale fixes (15 s since receipt, 30 s since fix time). Mock SOS coaching may show fresh coordinates with UTC fix time; otherwise it shows `Configured box address: 1455 California Ave`. The fallback is not a measured fix. A live outdoor fix on the installed receiver is **unverified**. This path does not send location to cloud or volunteers. The parser follows the [u-blox 7 receiver protocol specification](https://content.u-blox.com/sites/default/files/products/documents/u-blox7-V14_ReceiverDescriptionProtocolSpec_%28GPS.G7-SW-12001%29_Public.pdf).

Any displayed sample or derived pulse value shows value, unit, device and time without an extra experimental badge. Only show BPM from a fresh `quality:valid` event; do not call a computed value a direct chip reading. The agent can describe the result but does not use it to diagnose or choose the fictional scenario's steps. A consenting volunteer starts each reading; measurements are not stored by default.

Use [sensor contracts](../contracts.md) and [hardware notes](../hardware-power.md). Acceptance: real fresh reading, reconnect, no reading, wrong device, and volunteer change are tested on the selected hardware.
