# Firmware handoff — tested board profile, integrated build in progress

The [PlatformIO firmware](../../firmware/README.md) now targets the actual ESP32-WROOM-32 wiring: GPIO33 for the NC lid switch, GPIO18/19/23 for the three resistor-equipped LEDs, and GPIO21/22 for the MAX30102 at 100 kHz. Mount switch and buzzer outputs are disabled because they are not wired. The code builds, is flashed, and the Pi adapter has verified hello, LED ACKs, a fresh raw sensor result and null BPM with no finger. On-finger pulse accuracy and the installed lid mechanism remain unverified. The Pi's shared serial schema is `packages/contracts/src/serial.ts` protocol `1.1`. The six-slot kit wiring and the larger `2.4` envelope below remain proposed.

The selected classic ESP32-WROOM-32 development board reads the lid switch and reports debounced changes over its USB-C connection to the Pi. It is also the proposed controller for one low-current compartment LED per kit slot, each on a safe output GPIO with its own series resistor. The board's USB-to-UART bridge is the data link; verify its actual USB identity when it arrives. The Pi remains powered and owns the screen, camera, audio, cloud transport, and agent client. USB alone cannot wake a Pi that has been shut down. Optional battery telemetry and watchdog recovery are later work, not features of the current parts list.

On lid open, send `lid.opened` with a fresh boot ID and sequence number, then await Pi acknowledgment. If the Pi does not respond, the physical Clara Demo label remains visible; an LED/fault indication is optional until parts are selected. Do not repeatedly reset the Pi during an active session. On close, send `lid.closed`; the Pi ends media capture and returns to idle. Do not shut down the Pi while the only control path is USB unless accepting cold boot/manual restart. The switch must be debounced and wired to a safe 3.3 V GPIO, avoiding ESP32 boot-strapping pins.

For the proposed six-slot integration, accept only a bounded `light.set.request` from the Pi after manifest checks. Turn all other channels off before turning the requested one on; clear lights on lid close, Stop, reset or lease expiry. The implemented three-light serial command drives GPIO18/19/23 with a capped lease, but does not yet verify a supply-to-slot mapping or implement the larger `2.4` request envelope. Future GPIOs must avoid boot-strapping pins and conflicts with the switch and MAX30102 I²C. Each LED needs its own resistor; 12 V LEDs require external switching drivers.

For the proposed [anti-theft](anti-theft.md) features, the ESP32 also reads a mount-removal switch (debounced like the lid switch; send `mount.removed` / `mount.restored`) and drives a buzzer on `alarm.set.request`. Start the buzzer off, honor `off` immediately, and clear the buzzer on lease expiry, lid close, USB disconnect or reset. The ESP32 only reports switch states; the Pi decides whether an open or removal needs a flag.

Interface: [USB serial events in contracts](../contracts.md). Remaining acceptance: switch bounce does not create duplicate sessions; MCU restart and USB reconnect recover; the Pi shows a visible error if the lid controller is missing; no stale or wrong kit slot is lit. Proposed mount and buzzer behavior needs hardware before verification. See [hardware assumptions](../hardware-power.md). The current pin map is in [the firmware guide](../../firmware/README.md).
