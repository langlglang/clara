# Firmware handoff — proposed

The selected classic ESP32-WROOM-32 development board reads the lid switch and reports debounced changes over its USB-C connection to the Pi. It is also the proposed controller for one low-current compartment LED per kit slot, each on a safe output GPIO with its own series resistor. The board's USB-to-UART bridge is the data link; verify its actual USB identity when it arrives. The Pi remains powered and owns the screen, camera, audio, cloud transport, and agent client. USB alone cannot wake a Pi that has been shut down. Optional battery telemetry and watchdog recovery are later work, not features of the current parts list.

On lid open, send `lid.opened` with a fresh boot ID and sequence number, then await Pi acknowledgment. If the Pi does not respond, the physical Clara Demo label remains visible; an LED/fault indication is optional until parts are selected. Do not repeatedly reset the Pi during an active session. On close, send `lid.closed`; the Pi ends media capture and returns to idle. Do not shut down the Pi while the only control path is USB unless accepting cold boot/manual restart. The switch must be debounced and wired to a safe 3.3 V GPIO, avoiding ESP32 boot-strapping pins.

For compartment lighting, accept only a bounded `light.set.request` from the Pi while the lid is open, the USB link is connected, and the channel, sequence and deadline are valid. Turn all other channels off before turning the requested one on; clear all lights on lid close, `light.clear.request`, USB disconnect, controller reset, or a short command lease expiry. A command result confirms the GPIO output state the firmware attempted, not that the physical LED emitted light. Start all LED outputs off. Exact GPIOs remain unselected and must avoid boot-strapping pins and conflicts with the switch and MAX30102 I²C. The linked 3 V prewired LEDs need a checked series resistor per LED; if the team instead selects the 12 V LEDs, add external switching drivers and do not connect 12 V to any ESP32 pin.

For the proposed [anti-theft](anti-theft.md) features, the ESP32 also reads a mount-removal switch (debounced like the lid switch; send `mount.removed` / `mount.restored`) and drives a buzzer on `alarm.set.request`. Start the buzzer off, honor `off` immediately, and clear the buzzer on lease expiry, lid close, USB disconnect or reset. The ESP32 only reports switch states; the Pi decides whether an open or removal needs a flag.

Interface: [USB serial events in contracts](../contracts.md). Acceptance: switch bounce does not create duplicate sessions; MCU restart does not confuse ordering; USB reconnect recovers; the Pi shows a visible error if the lid controller is missing; stale LED commands never leave the wrong slot lit; mount-switch bounce sends one event; the buzzer never stays on after `off`, lid close or USB disconnect. See [hardware assumptions](../hardware-power.md). Exact GPIO and switch wiring remain open until the board is in hand.
