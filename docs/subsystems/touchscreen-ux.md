# Touchscreen UX

**Demo implemented:** the Pi serves an 800 × 480 kiosk view with an idle state, answer/question/item/guidance cards, captions, status banners, and a persistent simulated SOS button. **Demo verified on Pi:** the deployed idle screen shows MIC OFF, online state, and only the SOS touch action; card rendering is covered by tests but has not been checked on the physical screen. **Proposed:** generated diagrams, sensor-reading and handoff cards, source-checked media, and synchronized speech segments. See [conversation runtime](../conversation-runtime.md).

The screen is an output surface for Clara, not a menu the bystander must operate. Lid closed: microphone off, simple idle state, simulated SOS still available. Lid open: listening begins and the screen invites the person to speak. Opening the lid does not start guidance or contact the model. A spoken request can result in a brief answer, question, picture, kit location, actual sensor reading with time and units, or a source-linked guidance panel. No Next, Back, Repeat, Talk, or branch buttons are shown. The agent may keep a useful visual in place while the conversation pauses.

The only primary touch action is **SOS**. It opens a clearly simulated countdown and mock 911 coaching screen, reachable with the lid closed, offline, and without the agent. Cancel and return controls belong only to that overlay. A model failure does not cover the SOS button. The screen never claims a real call was made. Responder banners state only confirmed network status.

For a proposed presentation card, the Pi validates a `presentation_id`, source-linked asset, matching spoken segments, and any inventory or sensor reference before committing. Item cards name a slot only from the verified layout revision; the LED is a redundant cue. Reading cards show the connected device, value, units, timestamp and quality. An unavailable or stale reading displays no number. Camera interpretation carries uncertainty and capture time. The presenter highlights the current spoken segment and retains captions when audio fails. A new user utterance cancels obsolete speech and render work; old tool results cannot replace the newer visual.

The current demo's `screen-view/1.1` renderer accepts `answer`, `question`, `guidance`, `item`, `diagram`, `reading`, `handoff`, and `status` card kinds. Only the first four have producers. Segment synchronization, camera preview, and sensor cards are **proposed**. Offline, the existing screen retains its last committed content and mock SOS; cloud conversation is unavailable. Test the actual HDMI/USB display for readability, contrast, touch target size, and a single-action path to mock SOS. Avoid using small status text as the only way to convey a critical state.
