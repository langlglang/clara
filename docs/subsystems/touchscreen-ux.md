# Touchscreen UX

**Demo implemented:** the Pi serves an 800 × 480 kiosk view with an idle state, answer/question/item/guidance cards, a small approved illustration catalog, hardware-backed pulse and consented camera result cards, captions, status banners, simulated SOS, and a speaker-mute button. A closed lid blanks the UI to black; touching it reveals the controls for 15 seconds. **Demo verified on Pi:** the owner saw the larger item diagram and the 911 Guide button after deployment. Black-screen wake, mute, and live result cards still need a focused physical check. **Proposed:** generated diagrams, handoff cards, and synchronized speech segments. See [conversation runtime](../conversation-runtime.md).

The screen is an output surface for Clara, not a menu the bystander must operate. The kiosk stylesheet hides the mouse cursor across the full-screen touch interface; touch controls still work. Lid closed: microphone off, simple idle state, simulated SOS still available. Lid open: listening begins and the screen invites the person to speak. Opening the lid does not start guidance or contact the model. A spoken request can result in a brief answer, question, picture, kit location, actual sensor reading with time and units, or a source-linked guidance panel. No Next, Back, Repeat, Talk, or branch buttons are shown. The agent may keep a useful visual in place while the conversation pauses.

The primary touch actions are **SOS** and **Mute Clara**. Mute stops current speech and suppresses later speech and short cues; it leaves the microphone, screen replies, and SOS active. SOS opens a clearly simulated countdown and mock 911 coaching screen, reachable with the lid closed after a tap to wake the black screen, offline, and without the agent. Cancel and return controls belong only to that overlay. A model failure does not cover the SOS button. The screen never claims a real call was made. The nearby-emergency banner and its interruptive alarm are hidden in this kiosk view; confirmed responder status remains visible.

For a proposed presentation card, the Pi validates a `presentation_id`, source-linked asset, matching spoken segments, and any inventory or sensor reference before committing. Item cards name a slot only from the verified layout revision; the LED is a redundant cue. Reading cards show the connected device, value, units, timestamp and quality. An unavailable or stale reading displays no number. Camera interpretation carries uncertainty and capture time. The presenter highlights the current spoken segment and retains captions when audio fails. A new user utterance cancels obsolete speech and render work; old tool results cannot replace the newer visual.

The current demo's `screen-view/1.2` renderer accepts `answer`, `question`, `guidance`, `item`, `diagram`, `reading`, `handoff`, and `status` card kinds. A three-slot item lookup makes the tray diagram the dominant visual, with the item name and slot label below it. The Pi marks the LED cue active only after board acknowledgment and clears it at lease expiry. `diagram` uses the original, allowlisted illustrations in `packages/contracts/src/visuals.ts`; hardware-backed pulse and consented camera observations have result cards. The draft superficial-cut visual is reachable only for an explicitly described minor cut or scrape and shows its versioned, source-linked rinse-and-cover image as a large guidance card; content review is pending. Segment synchronization and live camera preview are **proposed**. Offline, the existing screen retains its last committed content and mock SOS; cloud conversation is unavailable. Test the actual HDMI/USB display for readability, contrast, touch target size, and the wake-then-SOS path while closed. Avoid using small status text as the only way to convey a critical state.
