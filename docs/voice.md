# Voice conversation

**Demo implemented:** the Pi listens only while the lid is open, ends a clip using voice activity detection, and sends one turn to the box API. The cloud turn can use Cartesia speech-to-text, a constrained Claude decision, and Cartesia text-to-speech; a keyword stub works without keys. The Pi has local speech fallback. Cartesia replies use a 1.5× generation speed; the local fallback keeps its own voice rate. The current model selects at most one action from a scenario-specific schema. A mock emergency fact worker can ask a fixed question through the same Clara voice and receive a source-linked user reply. **Demo verified on Pi:** the owner heard the requested Cartesia lid greeting, and a live open-lid “Where are the scissors?” request produced a reply and lit the top-left compartment. A silent clip sent to the live cloud returned no spoken reply; the new false-trigger filter and emergency question bridge still need physical venue verification. **Proposed:** one persistent user-facing Core Clara with a broader tool loop and future independent caller; see [conversation runtime](conversation-runtime.md).

Opening the lid creates a local session, plays the fixed 4.64-second, 1.5× greeting from `content/audio/clara-greeting-v3-fast.wav`, then enables the microphone. The scripted greeting is the owner's exact requested demo copy; it does not change the agent's no-diagnosis policy or make the mock 911 guide a real call. Opening the lid makes no model call and does not show the first scenario panel. Closing the lid stops capture and cancels active voice work. Each final utterance is a candidate request. Silence, mic noise shorter than the endpoint threshold, and partial transcripts must not request model work. The user never needs the screen to begin or continue talking.

```text
lid open → local mic starts → final utterance → POST /v1/boxes/{id}/turns
  → optional speech-to-text → model decision → server validation
  → action on Pi + optional synthesized speech → mic resumes
lid close → stop mic, speech and in-flight turn
```

The current endpoint uses 16 kHz mono WAV held in memory, 20 ms VAD frames, 0.7 s end silence, 0.3 s minimum speech, and a 15 s maximum clip. The endpointer learns the microphone's initial room level rather than treating its ambient hiss as continuous speech; on the installed Pi, room audio measured about -41 dBFS, above the old fixed -48 dBFS threshold. Its initial floor is capped at -32 dBFS so a loud first speech frame can still start promptly, while steady room sound around -25 dBFS remains below the relative speech threshold. This energy detector cannot reliably separate speech from every loud or changing noise; venue testing and a trained VAD remain follow-up work. It is half-duplex: capture pauses during box speech to avoid hearing itself. Voice interruption during playback needs echo cancellation and remains proposed. The box has an 8 s deadline and uses a fixed failure line on timeout; it keeps the last visual and simulated SOS available. The screen can mute speaker output while leaving the mic, visuals, and mock SOS active. There is no touch Talk, Next, Back, or Repeat control. Cloud conversation is unavailable during a disconnect.

A turn carries session ID, language, recent turns, current scenario ID/step if any, allowed content IDs, questions, inventory, and available visual IDs. The server rebuilds a strict schema each turn and checks the model result again. With `select_step`, the server resolves the chosen ID against its own versioned scenario bundle and asks Cartesia to voice that exact text. The Pi verifies the returned text matches its local panel, then plays the WAV while showing that panel; if TTS fails, it speaks the same text locally. The model's suggested wording is never used as guidance. `ask_clarifying` uses an approved question; `locate_item` resolves a verified manifest item; `suggest_sos` starts the **simulated** countdown; `start_triage` is offered only where enabled. `record_usage` is currently **not offered** because the minimal screen has no confirmation control. The protocol still recognizes it for compatibility. The model cannot return its own measurement or a diagnosis. A generic `presentation.show` card and multiple background jobs are proposed, not part of this turn API.

`voice-turn/0.6` makes an explicit spoken request to take a photo or use the camera authorize one cloud-bound frame in the current lid session; there is no second confirmation turn. The Pi checks that finalized request before capture, and each grant is consumed once. The old `capture_camera` action remains in the wire type but is not offered or accepted. `read_pulse`, server-owned `core_context`, and bounded background results continue. The Pi requires a real ESP32 pulse event for any number. Core can keep talking while a read or inspection finishes. The server only returns uncertain fixed-category camera observations. The unrestricted multi-call planner remains proposed.

`voice-turn/0.4` adds optional `available_visuals` and `show_visual{visual_id}`. The Pi offers only original assets present on disk and, for equipment illustrations, only items stocked in its kit. The server replaces model wording with a fixed catalog caption and Cartesia voices it when available. The Pi resolves the ID to a local URL, verifies the caption, and shows a large illustration; it never follows a model URL. The first catalog contains a three-slot overview and illustrations of scissors, gloves, gauze, antiseptic towelettes, adhesive bandages, medical tape, and an instant cold pack. These are identification and orientation art, not treatment diagrams. `voice-turn/0.3` added an optional pending mock-emergency question with `task_id`, `question_id`, and fixed prompt. If the current utterance answers it, the model selects `answer_emergency_question` with those IDs only; the Pi routes the exact finalized transcript, linked to its `report.heard` event, to the independent mock fact worker. An unrelated utterance remains in the normal conversation. `0.2` had already made selected guidance carry canonical text and optional Cartesia WAV; the server rejects unknown scenario/step IDs instead of voicing model or box-supplied text. Older `0.1` through `0.5` requests are rejected. The current bleeding scenario entry no longer says “step by step” or tells the user to tap a removed button.

The server rejects a reply promising rescue without acceptance, claiming a diagnosis, or falsely reassuring about the outcome. It retries an invalid model shape once, then returns a fixed line. Obvious speech-to-text artifacts such as `[noise]`, punctuation-only output, and filler-only output such as “um” are dropped before the model is called; the Pi silently resumes listening. Short requests such as “help”, “yes”, “no”, “SOS”, and item names still pass. This small transcript filter does not prove that a clip contains speech, so occasional false turns remain possible. Speech-to-text failure, model timeout, or network loss never produces a guessed answer. Sensor reads must come from wired hardware with units and time. An explicit spoken camera request is one-frame consent in that lid session; uncertain interpretation must be described as uncertain. Audio and transcripts are not written to ordinary logs; see [privacy and security](privacy-security.md).

Latency targets, not measured guarantees: about 700 ms for speech endpointing and 3–4 s from end of speech to first response. The current server turn budget is 6 s; the Pi deadline is 8 s. Later streaming speech and synchronized visual segments are specified in [conversation runtime](conversation-runtime.md).
