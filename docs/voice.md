# Voice conversation

**Current playback choice:** Clara keeps the microphone paused while she speaks because the installed speaker can leak into it. Ordinary model replies are prompted to use one sentence of roughly twenty words; source-linked scenario panels retain their recorded wording. In a guided flow with exactly one offered next panel, a bare acknowledgement such as “Got it” advances through a narrow server-owned fast path, with the same action and canonical-text checks on the Pi. On the arm-gauze panel, a request to teach or show how to apply, place, wrap, or use the gauze or the item just named opens the pressure visual through the same path; a simultaneous dispatcher request starts in the background. Worsening conditions, missing-gauze reports, and unrelated questions still go to the model. The server records action and timing metadata without speech content; a failed canonical lookup falls back to the ordinary model path. A live combined request previously missed the fast path and timed out in the model; the broader phrase guard has automated tests and still needs a physical retest.

**Clarifying question playback fix (implemented in code; live retest pending):** the server replaces any model wording for `ask_clarifying` with the selected versioned question. The Pi displays that question; the voice loop speaks the server reply once. The Pi no longer queues its own second copy. A scenario test checks the display and absence of duplicate local speech.

**Demo implemented in code:** the Pi listens only while the lid is open, ends a clip using voice activity detection, and sends one turn to the box API. The cloud turn can use Cartesia speech-to-text, a constrained Claude decision, and Cartesia text-to-speech; a keyword stub works without keys. The Pi has local speech fallback. Cartesia replies use a 1.5× generation speed; the local fallback keeps its own voice rate. A turn can launch distinct background SOS, pulse, and camera tasks while presenting one approved guide, item location, or illustration. A mock emergency fact worker can ask a fixed question through the same Clara voice and receive a source-linked user reply. **Demo verified on Pi:** the owner heard the requested Cartesia lid greeting, and a live open-lid “Where are the scissors?” request produced a reply and lit the top-left compartment. The new multi-task turn has automated tests but still needs a live voice check. **Proposed:** a broader multi-call planner and future independent caller; see [conversation runtime](conversation-runtime.md).

Opening the lid creates a local session, plays the fixed 4.64-second, 1.5× greeting from `content/audio/clara-greeting-v3-fast.wav`, then enables the microphone. The scripted greeting is the owner's exact requested demo copy; it does not change the agent's no-diagnosis policy or make the mock 911 guide a real call. Opening the lid makes no model call and does not show the first scenario panel. Closing the lid stops capture and cancels active voice work. Each final utterance is a candidate request. Silence, mic noise shorter than the endpoint threshold, and partial transcripts must not request model work. The user never needs the screen to begin or continue talking.

```text
lid open → local mic starts → final utterance → POST /v1/boxes/{id}/turns
  → optional speech-to-text → model decision → server validation
  → action on Pi + optional synthesized speech → mic resumes
lid close → stop mic, speech and in-flight turn
```

The current endpoint uses 16 kHz mono WAV held in memory, 20 ms VAD frames, 0.7 s end silence, 0.3 s minimum speech, and a 15 s maximum clip. The endpointer learns the microphone's initial room level rather than treating its ambient hiss as continuous speech; on the installed Pi, room audio measured about -41 dBFS, above the old fixed -48 dBFS threshold. Its initial floor is capped at -32 dBFS so a loud first speech frame can still start promptly, while steady room sound around -25 dBFS remains below the relative speech threshold. This energy detector cannot reliably separate speech from every loud or changing noise; venue testing and a trained VAD remain follow-up work. It is half-duplex: capture pauses during box speech to avoid hearing itself. Voice interruption during playback needs echo cancellation and remains proposed. The box has an 8 s deadline and uses a fixed failure line on timeout; it keeps the last visual and simulated SOS available. The screen can mute speaker output while leaving the mic, visuals, and mock SOS active. There is no touch Talk, Next, Back, or Repeat control. Cloud conversation is unavailable during a disconnect.

A turn carries session ID, language, recent turns, current scenario ID/step if any, allowed content IDs, optional guided scenario IDs, questions, inventory, and available visual IDs. The server rebuilds a strict schema each turn and checks the model result again. With `select_step`, the server resolves the chosen ID against its own versioned scenario bundle and asks Cartesia to voice that exact text. The Pi verifies the returned text matches its local panel, then plays the WAV while showing that panel; if TTS fails, it speaks the same text locally. The model's suggested wording is never used as guidance. `ask_clarifying` uses an approved question; `locate_item` resolves a verified manifest item; `suggest_sos` starts the **simulated** countdown; `start_triage` is offered only where enabled. `record_usage` is currently **not offered** because the minimal screen has no confirmation control. The protocol still recognizes it for compatibility. The model cannot return its own measurement or a diagnosis. `launch_tasks` can start distinct SOS, pulse, and camera jobs from one turn while selecting one foreground guide, item location, or illustration. The box starts SOS first, then shows the selected content. It uses the server's canonical text and keeps that visual on screen when a call status arrives. Other kinds of parallel jobs and a generic `presentation.show` card remain proposed.

`voice-turn/0.9` retains the `0.6` behavior in which an explicit spoken request to take a photo or use the camera authorize one cloud-bound frame in the current lid session; there is no second confirmation turn. The Pi checks that finalized request before capture, and each grant is consumed once. The old `capture_camera` action remains in the wire type but is not offered or accepted. `read_pulse`, server-owned `core_context`, and bounded background results continue. The Pi requires a real ESP32 pulse event for any number. Core can keep talking while a read or inspection finishes. A multimodal image call returns a detailed visual-only observation; Core Clara uses it as uncertain context to answer the original question in a separate no-action turn. The unrestricted multi-call planner remains proposed.

`voice-turn/0.4` adds optional `available_visuals` and `show_visual{visual_id}`. The Pi offers only original assets present on disk and, for equipment illustrations, only items stocked in its kit. The server replaces model wording with a fixed catalog caption and Cartesia voices it when available. The Pi resolves the ID to a local URL, verifies the caption, and shows a large illustration; it never follows a model URL. The first catalog contains a three-slot overview and illustrations of scissors, gloves, gauze, antiseptic towelettes, adhesive bandages, medical tape, and an instant cold pack. These are identification and orientation art, not treatment diagrams. `voice-turn/0.3` added an optional pending mock-emergency question with `task_id`, `question_id`, and fixed prompt. If the current utterance answers it, the model selects `answer_emergency_question` with those IDs only; the Pi routes the exact finalized transcript, linked to its `report.heard` event, to the independent mock fact worker. An unrelated utterance remains in the normal conversation. `0.7` adds `start_guidance{scenario_id}` for any loaded bundle marked `guided: true`. The model may choose a paced guide when it fits, then waits for a clear spoken completion before `select_step` moves to an offered next panel. Questions and interruptions stay in the same conversation. The server and Pi both check completion, and the Pi verifies the same-turn transcript and exact local panel text. The current English guide bundles are a superficial cut and an arm wound; both are draft content. The cloud provider schema no longer includes unsupported numeric limits when triage is offered, while Zod still validates those limits. `0.2` had already made selected guidance carry canonical text and optional Cartesia WAV; the server rejects unknown scenario/step IDs instead of voicing model or box-supplied text. Older `0.1` through `0.8` requests are rejected. The current bleeding scenario entry no longer says “step by step” or tells the user to tap a removed button.

The server rejects a reply promising rescue without acceptance, claiming a diagnosis, or falsely reassuring about the outcome. It retries an invalid model shape once, then returns a fixed line. An unspecified finger cut cannot trigger the severe-bleeding panel: if selected, the server instead asks whether it is small and shallow or bleeding heavily. Obvious speech-to-text artifacts such as `[noise]`, punctuation-only output, and filler-only output such as “um” are dropped before the model is called; the Pi silently resumes listening. Short requests such as “help”, “yes”, “no”, “SOS”, and item names still pass. This small transcript filter does not prove that a clip contains speech, so occasional false turns remain possible. Speech-to-text failure, model timeout, or network loss never produces a guessed answer. Sensor reads must come from wired hardware with units and time. An explicit spoken camera request is one-frame consent in that lid session; the multimodal interpretation can describe visible spatial detail and what remains unclear. It never infers severity from the image. Audio, transcripts and frames are not written to ordinary logs; see [privacy and security](privacy-security.md).

Latency targets, not measured guarantees: about 700 ms for speech endpointing and 3–4 s from end of speech to first response. The current server turn budget is 6 s; the Pi deadline is 8 s. Later streaming speech and synchronized visual segments are specified in [conversation runtime](conversation-runtime.md).

For a camera request, one multimodal model call creates a structured, detailed description of the single frame. The cloud keeps it for two minutes in the matching Core session, then a no-action voice turn lets Clara answer the question that prompted the photo in her normal voice. The Pi discards that background answer if the person speaks again before it arrives. A later question can still use the short-lived description. The photo is not a diagnosis, treatment decision, or sensor reading; Clara asks the person to confirm any image detail that would change guidance. If image inspection fails, the model never receives an invented description. These `voice-turn/0.9` and `camera-inspect/0.2` changes require matching cloud and Pi builds.
